01 · 클래스 수보다 반복되는 규약이 문제

현재 구조는 큰 기능 구분 자체가 잘못된 것은 아닙니다. 개선 효과가 큰 곳은 서버/클라이언트에 복제된 처리 흐름과 여러 객체가 함께 알아야 하는 메모리·세션 소유권입니다.

큰 세 파일이 전체 물리 행 수의 약 32%입니다. 다만 장문의 설계 주석이 포함되므로 행 수를 실행 코드 복잡도나 제거 가능한 코드량으로 해석하면 안 됩니다. 예상 절감률·성능 향상 수치는 측정하지 않았습니다.

03 · 현재 폴더 구분 평가

현재 폴더판단권장 조정
Buffer대체로 적절수신 링/패킷 추출, 송신 큐, 공유 송신은 응집도가 있다. PreDefine.h는 내용에 맞게 BufferLimits 또는 ProtocolLimits로 나누고 이름을 명확히 한다. 크기 제한의 단일 원천을 정한다.
Core범위가 넓음IOCPCore는 IOCP 런타임, IOCPServer/Client는 전체 조립·접속·프로토콜 처리다. Runtime으로 이름을 바꾸고 transport 구현과 orchestration을 구분한다. 형제 Module/Core와 이름 혼동도 줄인다.
HandlerTable폴더는 과도하게 작음클래스 자체는 등록/조회 검증이라는 역할이 있다. 삭제하지 말고 Job·Scheduler와 Dispatch로 묶는다.
Job + Scheduler함께 묶기 권장작업 정의, 핸들러 매핑, 실행·대기가 같은 처리 흐름을 이룬다. SessionJobQueue도 Dispatch로 이동하면 찾기 쉽다. 클래스 통합과 폴더 통합은 별개다.
Session대체로 적절, 책임은 조정연결 상태와 풀을 유지하되 잡 큐는 Dispatch, accept 슬롯은 Transport/Runtime 쪽으로 이동 가능하다. 풀의 liveness 정책은 별도 함수로 이동한다.
Memory유지TLS 캐시와 전역 저장소는 한 모듈로 유지. EnginePoolBuilder와 Job/Packet 생성 helper는 엔진 조립·객체 정책이므로 Runtime/Dispatch/Buffer 쪽으로 분리해 Memory의 상위 모듈 의존을 줄인다.
NetworkTransport로 확장SocketOption과 OverlappedEx는 플랫폼 IO 성격이다. IOCPCore를 옮긴다면 IOCP port/worker 구현과 함께 배치한다.
Protocol유지wire 데이터 형식과 ID 범위를 모은 경계는 적절하다. 시스템 응답→DisconnectReason 변환은 wire 정의와 분리 가능하다.
Diagnostics유지로그 연결과 위반 카운터는 횡단 관심사다. API와 내부 assert를 구분하되 작은 파일을 억지로 합칠 이유는 없다.

HandlerTable이 두 파일뿐이라는 이유만으로 클래스를 없앨 필요는 없습니다. 폴더는 기능 탐색 단위, 클래스는 상태와 불변식의 단위로 따로 판단합니다.

P1F02 / 구조 핵심 · 변경 위험 높음

패킷 소유권을 포인터 관례에서 명시적인 계약으로 바꾸기

현재 수신은 const char*, 송신 이전은 void**를 사용한다. 작업 실행 후 스케줄러가 패킷을 반납하지만, 클라이언트 핸들러는 ClearCurrentJobData()로 세션 내부의 현재 작업을 수정해 반납을 막는다. 큐·스케줄러·서비스가 동일한 소유권 규약을 모두 알아야 한다.

P1F04 / 검색 범위 내 미사용 · 공개 호환성 확인 필요

실제 사용하지 않는 Job 일반화와 작은 잔여 선언 정리

Job은 PACKET/DB/SYSTEM union과 void* target을 갖지만, 확인한 생성 API는 SetPacketJob이고 엔진의 제출 경로도 PACKET이다. 워크스페이스의 C++ 소스 검색에서 DB/SYSTEM 값 사용은 Execute의 분기만 발견했다. CommonHandlerFunc, PACKET_OWNERSHIP도 선언 외 사용을 찾지 못했다.

제안: 이 DLL의 책임이 패킷 처리라면 PacketJob으로 좁히고 ISession*와 PacketHandlerFunc를 직접 저장한다. DB 작업은 DB/서비스 계층에서 관리한다. 실제 범용 잡 요구가 있다면 먼저 각 작업의 payload 반납 계약을 정의해야 한다.

이유: 서버 스케줄러와 큐 Reset은 모든 data를 패킷으로 반납하지만, 클라이언트 스케줄러는 PACKET만 반납한다. 현재 PACKET 전용 사용에서는 문제가 드러나지 않아도, DB 분기를 활성화하면 소유권 의미부터 달라진다. 단순히 switch 몇 줄을 지우는 문제가 아니다.

P1F05 / 정적 API 불일치 확인 · 대체 구성 빌드 미실행

TLS/Slab 이중 백엔드의 지원 여부를 명확히 하기

ENGINE_USE_TLS_MEMORY_POOL=0은 SlabMemoryPool을 선택하지만, 공통 빌더가 호출하는 SetCommitLimit, GetBinIndex, GetBinBlockSize는 현재 SlabMemoryPool 선언에 없다. 따라서 이 소스 상태의 전체 엔진은 매크로만 바꿔 교체할 수 있는 구조가 아니다. Slab 구현은 16바이트보다 큰 정렬 요청도 경고만 남기며, Job은 64바이트 정렬을 선언한다.

권장: TLS를 유일한 운영 백엔드로 확정한다면 Slab 코드는 비교용 benchmark/legacy 대상으로 분리하고, 운영 alias의 조건 분기를 없앤다. 두 구현을 정말 지원하려면 공통 API·정렬·종료 규약을 맞추고 두 구성 모두를 빌드/검증한다. 새 가상 allocator 계층을 만드는 것은 이 요구가 확인된 뒤에 한다.

유지할 구조: TlsMemoryPool → ThreadBlockCache / ThreadCacheRegistry → GlobalBlockPool은 캐시, 스레드 종료 관리, 전역 저장소라는 실제 책임 차이가 있다. Slab 대체 구현과 이 내부 계층을 같은 종류의 중복으로 보지 않는다.

P1F06 / 소유권 중복 확인 · 변경 위험 높음

초기화 실패·종료·재시작을 하나의 수명 계약으로 정리

StartServer/StartClient는 자원을 단계별 생성한 뒤 여러 지점에서 바로 false를 반환한다. 함수 내부에서 전체 기동을 되돌리는 공통 경로는 없으므로 호출자가 Stop을 책임져야 한다. 풀 네 포인터를 임시 EnginePools로 다시 조립하는 코드도 Stop/Destroy마다 반복된다.

P2F07 / 책임 분산 확인 · 조건부 통합
